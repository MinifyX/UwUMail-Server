# Security audit — release 0.34.0

Scope: everything new between `main` and `feat/backup-search` (`git diff main...feat/backup-search`,
lockfiles left out). This covers the search index over the snapshots' headers
(`crates/uwumail-backup/src/index.rs`), how backups and the catch-up fill it
(`crates/uwumail-backup/src/lib.rs` `backup`, `service.rs` `catch_up_index`, `run`), searching and
restoring a person's own mail (`service.rs` `search_mail`, `backup_mail_contents`, `restore_mails`),
the JMAP extension `urn:uwumail:jmap:backups` (`crates/uwumail-jmap/src/methods/backup_email.rs`,
`session.rs`, `methods/mod.rs`), the wiring in `crates/uwumail-server/src/serve.rs` and the admin
setting in `crates/uwumail-web/src/routes/backups.rs`. Read only, nothing built or run.

## Summary

| Severity | Count |
| --- | --- |
| Critical | 0 |
| High | 0 |
| Medium | 2 |
| Low | 7 |
| Info | 4 |

Ownership holds. Every index query filters on `account_id` **and** `account_created_at`, and get
and restore look each id up again with the same owner. An id that belongs to someone else, or that
does not exist, gets the same `notFound` from the same query, so a guessed id tells nothing. Account
ids are not reused (`next_id`, migration 0048). After a whole-server restore to an older state, an
id can come back, but `created_at` (seconds) still tells the two accounts apart. `open` refuses a
call in a shared account before anything else (`ctx.shared`), and masked-only credentials never get
past `dispatch`. The JMAP ids (`k<n>`) go through `ids::parse`, which checks the length and digits.
`content_of` reads only the blob the owner's index row names, and checks its hash, whether it comes
from the local store or from the repository.

Every value reaches SQL as a bound parameter. `format!` puts in only constants (`COLUMNS`,
`SCHEMA`, `VERSION`). `like_pattern` escapes `%`, `_` and `\`, and every `LIKE` names `ESCAPE '\'`.
Snapshot databases are opened through `mailbox::open`, so PLAT-7 still holds: read only,
`trusted_schema = OFF`, values capped at `MAX_VALUE`, tables only, a 10-minute watchdog. `add`
streams the rows and stops at `MAX_MAILS`. A value of the wrong type ends in a rusqlite error, not a
panic. `dates::format` and `day_of` don't overflow or slice out of bounds on extreme timestamps.
`ingest` checks the quota on restore, twice. Errors reach the client only as
`serverUnavailable` with a fixed text, and the details go to the log.

The two Medium findings are about availability. Any person can open the backup storage and download
from it as often and as much as they like (B34-01). The catch-up holds the backup lock for as long
as it fetches every missing snapshot, which can be hours (B34-02).

## Findings

| ID | Severity | Location | Cause | Fix | Status |
| --- | --- | --- | --- | --- | --- |
| B34-01 | Medium | `crates/uwumail-backup/src/service.rs` `backup_mail_contents`, `restore_mails`, `open`; `crates/uwumail-jmap/src/methods/backup_email.rs` `get`, `restore` | Every `BackupEmail/get` and `/restore` call opens the repository again: a new SFTP session or S3 client and a read of `config.json`. Nothing limits how many such calls run, per account or for the server: up to 64 per request (`MAX_CALLS_IN_REQUEST`), and `maxConcurrentRequests` is advertised but not enforced. `get` holds up to 10 mail contents in memory at once, read with `BLOB_MAX` (1 GiB per object), plus a parsed copy of each. Restore downloads up to 50. Any user can use this to exhaust the server's memory, to open enough SFTP logins that the backup server rate-limits or bans the mail server (scheduled backups then fail), or to run up S3 egress by fetching the same large deleted mail again and again. | One semaphore for all user reads from the backups (1–2 at a time; a busy call answers `serverUnavailable` or waits briefly), plus at most one `BackupEmail/get` or `/restore` per request. Open the repository once per call at most, and only when an id actually needs the remote copy (`content_of` tries the local blob first). Skip `get` for mails above a size limit, checked against `size` from the index before downloading; the preview then shows headers only. Optionally a per-account rate limit like the other expensive methods. | fixed: one user read or restore at a time server-wide (semaphore); size skip not done |
| B34-02 | Medium | `crates/uwumail-backup/src/service.rs` `catch_up_index`, `run` | `catch_up_index` takes `LOCK_FILE` once and keeps it while it fetches and indexes every snapshot that is missing. After the upgrade that is all of them, because `index_stale` starts out `true` and the search is on by default, and each fetch is a whole database. For the whole time: a mailbox restore, a whole-server restore and a backup started from the command line get `Busy` ("a backup or a restore is running"), which is misleading. The scheduler loop is blocked, so a due backup waits, and it is skipped when the catch-up runs past the UTC day (`succeeded_today`). The loop doesn't look at `shutdown` during the catch-up either. | Take the lock per snapshot and release it in between. Between snapshots, stop when a backup is due, someone asks for one (`wakeup`), or shutdown comes, and leave `index_stale` set so the next round goes on. Optionally cap one round at a few snapshots, newest first. | fixed: lock per snapshot; stops for a due backup, a wakeup or shutdown |
| B34-03 | Low | `crates/uwumail-backup/src/service.rs` `catch_up_index`; `index.rs` `add` | A snapshot that cannot be added is only logged. That covers a damaged one, one with more than `MAX_MAILS` mails in all (a count over all accounts) and one stopped by the 10-minute watchdog. It stays missing, so every later catch-up, that is after every backup, downloads its whole database again. On a server with more than 5 million mails, no snapshot can ever be added, and all of them are fetched every day. | Remember failed snapshots in the index (name and reason, e.g. a `failed` table) and skip them until the index version or the server version changes. Count `MAX_MAILS` per account, or raise it for the index, which streams and doesn't hold the rows in memory. | accepted (retried after each backup) |
| B34-04 | Low | `crates/uwumail-backup/src/service.rs` `open` (called from `backup_mail_contents`, `restore_mails`); `crates/uwumail-backup/src/lib.rs` `Repository::open` | User calls open the repository with `Repository::open`, which writes a new `config.json` when the read finds none. A user request can therefore start a repository on a target the admin has just set, or rewrite the config when the storage wrongly reports it missing (wrong prefix, eventual consistency). On an SFTP target with no pinned host key, the user call pins the key and calls `save_settings` with the settings it read at its start. That can overwrite a change the admin saved in the meantime (lost update), for example switching the search back on or bringing back the old target. | User paths use `Repository::open_existing`. They never save settings: without a pinned host key they answer `serverUnavailable` until a backup has pinned it. | fixed: `open_existing`, no settings saved |
| B34-05 | Low | `crates/uwumail-backup/src/service.rs` `save_settings`, `catch_up_index`, `run_now`; `index.rs` `open`, `remove` | Switching the search off deletes the index files with `remove`, even while a catch-up or a backup has the index open. `catch_up_index` checks `user_search` only at its start, and `backup` gets the index path from the settings read at its start. Each later `add` calls `open`, which makes the index again. Headers stay on disk after the admin switched the search off, against docs/backups.md ("Switching the search off deletes the index"). Deleting `-wal` under an open connection can also damage the file being written. | `add` and `retain` check `user_search` again (or a generation counter that `save_settings` bumps) before they write, and don't create the file unless the catch-up asked for it. Do the delete in the scheduler under `LOCK_FILE`, not in `save_settings`. | fixed: index dropped after a backup or catch-up when the search is off |
| B34-06 | Low | `crates/uwumail-backup/src/index.rs` `open`, `search`, `get`, `add` | Every search and every get opens the index read-write and runs `PRAGMA journal_mode`, the schema and `PRAGMA user_version = 1`. That writes the database header, so each call needs the write lock. `add` writes a whole snapshot (up to 5 million rows) in one transaction. Meanwhile every search waits out `busy_timeout` (10 s) on a blocking thread and then fails. With another `user_version`, `open` deletes the files, even with other connections open, and calls itself again; if the delete fails (permissions, read-only volume), it recurses until the stack overflows and the process aborts. | Open read only for `search` and `get` (`SQLITE_OPEN_READ_ONLY`, no schema, no pragmas; a missing or foreign-version index answers "nothing found"). Set up the schema and change the version only in `add` and `retain`, under the lock. On a version mismatch, delete once and return an error instead of recursing. Commit `add` in batches (e.g. every 10,000 rows). | fixed: read-only open for search/get, no recursion |
| B34-07 | Low | `crates/uwumail-backup/src/service.rs` `backup_mail_contents`, `restore_mails`; `lib.rs` `backup` (retention/prune) | The index learns which snapshots retention deleted only at the next catch-up. That can be a long time: B34-02 delays it, and after an error it waits for the next backup. Meanwhile a query lists mail whose objects the backup's prune already removed. User reads don't hold the lock, so a prune can also remove an object under a running restore. Any error with one id ends the whole `get` or `restore` with `serverUnavailable`: a missing object, a `blob_hash` that doesn't parse (damaged snapshot) or a network error. The mails restored before it stay restored, but the answer doesn't say which. One damaged entry blocks every id after it in each attempt. | Report per id. A missing object or a damaged entry becomes `notFound` (get) or `notRestored: notFound` (restore), and a network error ends the call with the outcomes so far. Right after retention, `backup` calls `index::retain` with the remaining snapshot names, under the lock it already holds. | fixed in part: per-id `notFound`; retain stays in the catch-up after each backup |
| B34-08 | Low | `crates/uwumail-store/src/fetch.rs` `holds_message`; `service.rs` `restore_mails`; `backup_email.rs` `in_mailbox` | When the mail has a Message-ID, "already there" means only that some mail in the account has the same Message-ID. Whoever sends the person a mail can choose its Message-ID. Someone who knows or can guess the Message-ID of a mail the person deleted (a reply chain, a mailing list) can send a mail with that Message-ID. The deleted mail then can't be restored (`alreadyThere`), and `inMailbox` says it is still there. | Count a mail as there only if its `blob_hash` matches, or if both the Message-ID and the size match. Otherwise restore it; a duplicate is cheaper than a mail that can't be restored. | fixed: matched by `blob_hash` only |
| B34-09 | Low | `crates/uwumail-backup/src/service.rs` `restore_mails` | Two restores of the same ids running at once (two tabs, the app and the webmail, a retry after a timeout) both pass `holds_message` before either one has stored the mail, so each mail is stored twice. The quota bounds this, but it still adds to used storage. | A per-account lock (e.g. a `Mutex` keyed by `account_id` in `Inner`) around `restore_mails`, or check `holds_message` again inside the store transaction. | fixed by the B34-01 semaphore |
| B34-10 | Info | `crates/uwumail-backup/src/index.rs` `search` | `text` is matched with a leading-wildcard `LIKE` on three columns of every index row of the account, so there is a full scan each time. Without B34-01's limit, that can be up to 64 times per request. `from_addr` and `to_addr` hold JSON, so the words `name` and `email` match every mail. Only the person's own mail is affected, so nothing leaks. | Covered by B34-01's limit per request. Match on the extracted values (separate `from_text` and `to_text` columns) or, later, on FTS5 as the existing `shortcut:` comment says. | accepted |
| B34-11 | Info | `crates/uwumail-backup/src/service.rs` `catch_up_index`; `lib.rs` `fits_this_server` | The catch-up indexes every snapshot in the repository, without checking `manifest.hostname`. When two servers write to the same repository with the same key (a test server cloned from production, a migration done twice), the other server's mail is added under the local `(account_id, created_at)`. Today that only matters when an account on each server was made in the same second with the same id. | Skip snapshots whose `manifest.hostname` is not this server's (log it once). | accepted |
| B34-12 | Info | `crates/uwumail-backup/src/index.rs` (`cache/backup-index.db`); `service.rs` `BackupSettings::default`; docs/backups.md | The index holds the subject, senders and recipients of every mail in every snapshot as plaintext in the data directory, for the whole retention period, also when the backups themselves are encrypted. UwUMail leaves it out of its own backups, but host or volume backups of the data directory (VM snapshots, Docker volume backups) include it. The search is on by default, also on an upgrade, so existing servers start building it without the admin choosing it. | Create the file with mode 0600. State in docs/backups.md (and the privacy notes) that deleted mail's headers stay readable locally for the retention period. Consider off by default on an upgrade, or a one-time notice in the admin panel. | fixed: mode 0600, docs/backups.md; default stays on |
| B34-13 | Info | `crates/uwumail-jmap/src/methods/backup_email.rs` `get` | The preview runs `MessageParser::parse` on content from the backup without the depth and part limits that `ingest` enforces (`parse::read`, security-audit-0.16.0 SMTP-1/SMTP-4). Mail stored since 0.16.0 has passed those limits, so only older snapshots could hold mail that is nested too deeply. `restore` goes through `ingest` and is covered. | Run `uwumail_store::parse::read` (or the same check) before parsing. If it refuses, list the mail with headers only and no `textBody`. | fixed: `mime_limits::parse_message` |
